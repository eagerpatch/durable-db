"durable-db": patch
---

Less work that nothing asked for: at an object's first migration run, at every isolate's start, on every command line of a host CLI and in every build. Measured in Lagerverk's examples, CPU from V8 profiles and process counters.

- **A Durable Object reads `DEBUG` from its own env**, never from `process.env`: `SqliteDurableObject`'s constructor hands `env.DEBUG` to the debuggers. In workerd the first read of `process` builds Node's whole process object, its streams with it — the 8 ms of CPU that 0.14.1 had moved from every isolate's start to each object's first migration run (every new tenant's first call, and every tenant's after a deploy that adds a migration). The first request of a fresh isolate with a new object: 27.7 → 19.5 ms. With `nodejs_compat` both held the same values; a `DEBUG` var now works without it too.
- **`durable-db/type` parses a definition when its Type is first used** — a call, any property or method, its use in another Type — not when `type()` is called. Every isolate, the worker's and each Durable Object's, evaluates every `type()` at module scope as it starts, though a request validates one or two: an isolate's start 6.8 → 5.3 ms (1.2 ms of parsing at start, 0.16 ms at the first request instead). A malformed definition, which ArkType's types refuse at compile time, throws its `ParseError` at that first use. The IPv6 keyword's pattern is built at its first use too.
- **An action's args schema is compiled once per isolate, at its first use**: the transform compiled it at module scope and again at the call site's first call. One `__validator_X()` now serves the call site, the object's validator and `describeAction()`, and is kept by the module, so an action file that dev evaluates again after an edit validates its new args (the registry's cache by name kept the old schema until the dev server restarted).
- **Babel is required at the first parse**: `durable-db/cli` no longer loads it, so a host CLI that registers `db` pays nothing for it on a command line that parses nothing (`lagerverk --version`: 0.13 → 0.08 s of CPU). `tests/cli/startup.test.ts` fails when the built entry loads Babel.
- **Drizzle's values are imported from the modules that define them**, not from the indexes of `drizzle-orm` and `drizzle-orm/sqlite-core`, which load the rest of Drizzle: importing `durable-db/schema` loads 31 of drizzle-orm's modules instead of 104 (220 → 63 ms of CPU in a fresh Node process), `durable-db` 84 instead of 107 (305 → 262 ms), at every schema load of `db push`, `generate`, `status` and `validate`. A worker bundles 35 of Drizzle's modules instead of 39 (21 KB less).
- **The Vite plugin's `resolveId`, `load` and `transform` carry hook filters**, so Rolldown (Vite 8), Rollup ≥ 4.38 and Vite's dev server ≥ 6.3 call them only for the plugin's virtual modules, TypeScript and Drizzle's modules, instead of for every module (one app's build: 7 390 calls → 269). Each handler keeps its own checks, and a bundler without filters (Vite 5.4 on Rollup 4.27) calls them as before; a fixture builds alike under Vite 5.4, 6.2, 6.4, 7.3 and 8.3. Drizzle's modules are tagged side-effectful with no code in the answer, so their code is no longer handed back to the bundler.
