---
'durable-db': minor
---

The outbox says which database recorded a message, works out its tenant from what the build applied, and no longer lets one failing message hold back the rest — in 0.13 a message the sink could not take was retried with the 100 oldest forever, and nothing behind it was delivered. A message is buried only for a failure of its own, never during an outage of the sink, and an outage costs a bounded number of deliveries a round, whatever is recorded meanwhile.

- **The envelope names its database and its attempts.** `OutboxEnvelope` has `database` — the name the database is known by (the generated class's `databaseName`; a hand-written subclass without one, the name derived from its class name, else the class name) — and `attempts`, how many deliveries of it failed before this one (not counting tries while the sink was taken for down). A global database's instance key `'global'` and a per-tenant database's tenant named `global` were the same string, and the envelope said nothing else: a sink could not tell them apart.
- **The tenant is worked out from what the build applied, not by cutting the key at its last `__dev_`.** The generated classes know their database's `instance` (`databaseInstance`) and the suffix the build gives their keys (`devEpochSuffix = applyDevEpoch('', name)`: `__dev_<epoch>` in dev, nothing in production). A global database's instance has no tenant whatever its key; a per-tenant one's tenant is its key without exactly that suffix. So `envelope.tenantId` and `getTenantId()` inside an action answer a tenant named `global` as that tenant, and keep a tenant id that contains `__dev_` whole — in production it was cut. In dev every key carries an epoch, so a key that does not end with the current one is an earlier epoch's — an object `db reset` left behind, whose alarm still delivers what waits in its outbox — and its trailing `__dev_<epoch>` is cut: its tenant stays the tenant, not a made-up one with the old epoch in its name. The object hands its tenant to the action's DoContext store (`DoContext.tenantId`); a store built by hand without it is read as its key, `'global'` as no tenant, when no resolver is set.
- **In an action of a per-tenant database's object, `getTenantId()` answers the object's own tenant first.** It asked an installed resolver first, and the resolver an app installs with `setTenantIdResolver()` at its worker module's top level is installed in every object's isolate too (in dev the worker and the objects share one): so the object's tenant was never read, and a resolver that reads a request threw inside an action — or in the stub of another database's action it calls. Now an action running in a per-tenant object, and what it calls, gets that object's tenant, which cannot be wrong there, before any resolver. A global database's object (no tenant of its own), code outside any object, and an object's alarm — which runs no action, so the outbox sink included — ask the resolver as before: a sink reads the tenant from `envelope.tenantId`, and the stub of a per-tenant action it calls asks the resolver for its key. The one thing it changes: a resolver can no longer answer another tenant for an action of a per-tenant object.
- **Each message is retried on its own clock.** The alarm hands the sink only the messages that are due (the outbox's new `next_attempt_at`), oldest first, at most 100; a message the sink did not take is retried on its own backoff (5 s, doubling, at most 5 minutes) and the alarm is set to the earliest one due. No order is kept across a failure: a message recorded later may be delivered before an earlier one waiting for its retry.
- **A message that fails every delivery holding it is cut off from the others.** A delivery that fails whole — it throws, or its `{ retry }` names everything it did not give up on — does not say which message failed it, so the messages it leaves are split in two for their retry (the new `batch` column), each half a delivery of its own, until the bad one is alone: of 100 messages pushed together, one of them bad, the other 99 are delivered within seven retries (about ten minutes). A batch that fails while another delivery of the same alarm went through holds a message failing on its own: it is marked suspect (its `batch` negated) and never merged into another delivery again, so two or more bad messages hold back nothing either (`[bad, x, bad, y]`: x and y are delivered within 20 s).
- **One alarm, at most three deliveries.** The alarm groups the messages due by their batch and tries what no delivery has failed yet first, then what failed longest ago, suspect or not, so every batch gets its turn and one that just failed goes to the back; when the first delivery takes nothing, the second is tried. Once a delivery has taken anything, the sink works: everything else read but the suspect batches goes in one more delivery, and the suspect ones, each alone, use the calls left. When neither of the first two took anything and neither says anything of the sink (each a lone message that failed before), the third is tried. Recovery from a backlog goes 100 messages an alarm in at most three deliveries.
- **An outage of the sink is noticed and waited out.** Two deliveries in a row that take nothing, and say something of the sink — of several messages, suspect or not, or of one no delivery had failed yet (a lone message failing again may be its own) — and the sink is taken for down: the outbox's new `__outbox_sink` row says until when, and what those deliveries held is split, not counted. Nothing is tried before that (an alarm that fires earlier reads that one row and goes back to sleep); a message recorded meanwhile sets the alarm to that time, not to now, and waits with the rest. That next try hands the sink one message, and if that takes nothing another — what never failed first, then what failed longest ago, read from the whole table, a message tried going to the back — so the tries go round every message waiting, and a hundred that never go through, the oldest in the table, hide nothing behind them. What a try hands the sink keeps its attempts and its batch: never counted, never buried. The next try backs off as a message does; one that delivers anything ends it, and the rest it read goes in one delivery. In 0.13 an outage cost one delivery a round of retries plus one for every action that recorded a message (each set the alarm to now); now it costs up to two a round and nothing for what is recorded meanwhile. Measured with a sink that always throws, both versions with one probe: 2 000 waiting and nothing recorded, 42.6 minutes — 28 deliveries in 15 alarms (0.13.3: 14 in 14); a message recorded every minute for an hour — 36 in 21 (0.13.3: 63 in 63); one every 10 s for an hour — 35 in 19 (0.13.3: 361 in 361).
- **`maxAttempts` counts a failure of the message's own.** A message that the sink answered in `{ dead }`, or whose failure of its own reached `maxAttempts` — `durableDb({ outbox: { queue | module, maxAttempts } })`, default 100, about eight hours at the five-minute ceiling — is moved to the object's `__outbox_dead` table (message, instance key, `recorded_at`, attempts, last error, `dead_at`) and logged with `console.error`, naming how many and the table; it is never retried by itself and never dropped. A failure is its own when the delivery held it alone, or named it in `{ retry }` and delivered the others — and the sink delivered something else in the same alarm or since the message last failed (the outbox's new `failed_at`, and `__outbox_sink.delivered_at`, which an alarm that delivers anything moves on whenever a waiting message failed no earlier than it). A delivery that failed whole with others in it counts the attempt but buries none of them; a message is buried once it has failed alone at or past the cap. So a message delivered beside a bad one never goes down with it (`maxAttempts: 3`, one bad among ten: the nine are delivered); nothing is counted while the sink is taken for down, however long — an outage only suspect batches see is taken for one too — and nothing is buried (a Queue whose `sendBatch` always rejects, or a webhook that always throws, for twenty times `maxAttempts` rounds: nothing buried, everything delivered once it is back); and a lone message failing while nothing else gets through is retried at the five-minute ceiling, not buried, until something else is delivered. A sink that stops at a message it can never send and names everything after it in `{ retry }` has those buried with it at the cap — they were named, so their failures are their own: answer that one in `{ dead }`, or throw. An outbox 0.13 left is upgraded once, by `ALTER TABLE` (`next_attempt_at`, `batch`, `failed_at`), its rows' `attempts` set to 0: 0.13 counted each failure on every one of the 100 oldest, so its counts were its batch's.
- **A sink may settle a delivery one envelope at a time**: `deliver()` may answer `{ retry?, dead?, error? }` — of the envelope objects it was handed, those it could not deliver now (`retry`; retried together, not split, when it delivered the others: the sink said which) and those it never can (`dead`, moved to `__outbox_dead` at once, sparing them their retries); every other one counts as delivered. A throw still retries every envelope of the delivery.
- **The sink is handed a frozen list of its own.** `deliver(envelopes: readonly OutboxEnvelope[], …)` gets a frozen copy, and what it answers is matched by the envelope objects, never by their places in the list, so nothing a sink does to a list can make a message it never sent count as delivered. A sink that changes the list it is handed — chunking it with `splice()`, sorting it in place — fails loudly (a frozen array refuses it, and the delivery is retried whole); one that copies it first (`[...envelopes]`) chunks and sorts as it likes.
- **The Queue sink packs by bytes as well as by count.** `queueOutboxSink()` sent 100 messages to every `sendBatch`, so 100 messages of 3 KB (310 KB, over the 256 KB a `sendBatch` takes) were refused on every try, and nothing behind them was delivered; one message of 200 KB failed the 99 sent with it the same way. It now sends as few `sendBatch` calls as Cloudflare Queues takes — at most 100 messages and 256 KB each, a message's size its UTF-8 JSON plus the queue's 100 bytes — and sends each message with `contentType: 'json'`, so its size is its JSON's (a message is a JSON value already: its consumer gets the same body). A message over 128 KB, which no queue message holds, is not sent but answered in `{ dead }`, so it never fails the batch it would be in. A failed `sendBatch` answers the envelopes it left unsent; when it is the first, nothing went, and the delivery counts as failed whole — the queue's failure, no message's own.
- **What it costs.** The outbox has no index — each would be a billed row written per message, and the table is near-empty but for an outage. An alarm reads it at most twice — the messages due (by id, a scan that stops at the hundredth due, so it reads the whole table when fewer are due; at the sink's next try, by when they last failed, the whole table), then the earliest one waiting — and once when it finds the sink down; an alarm before the sink's next try, like each message recorded meanwhile, reads the one row of `__outbox_sink`. Around a failure an alarm writes the messages it tried (at most 100) and that row; a try while the sink is down writes the two messages it handed the sink and that row, and nothing else waiting is written, however long the outage (10 000 waiting, the second hour of an outage: 36 rows written; 0.13.3 wrote the 100 oldest every round, 1 200).
- `destroyDatabase()` no longer leaves the outbox unusable: the next message after it was refused with "no such table: __outbox". A delivery still in flight when it runs settles nothing on the storage that replaced the one it read (the object counts its storage generations), where it could have deleted, retried or buried a message recorded after the wipe that got the same id, or thrown "no such table".
- `createTestDatabase()`'s envelopes carry `database` and `attempts` too, and its `outbox` option is handed a frozen list of its own, as the sink is; its options `database` (default `'test'`) and `instance` (default: the action's own database's) name them.

**What a consumer changes.** `tenantOfInstanceKey(instanceKey)` is `tenantOfInstanceKey(instanceKey, { instance, devEpochSuffix? })`: a key alone cannot tell a global database's `'global'` from a tenant named so, and the one-argument call throws saying so. Code that builds `OutboxEnvelope`s (a sink's tests) adds `database` and `attempts`. A sink is typed `deliver(envelopes: readonly OutboxEnvelope[], …)` — one written against `OutboxEnvelope[]` still type-checks — and one that changes the list it is handed (`splice`, `sort`, `push`, …) copies it first, since the list is frozen. A sink that worked around the tenant — reading `instanceKey` itself, or deciding `'global'` from whether the app has a global database — can use `envelope.tenantId` and `envelope.database` as they are. A sink that moved a message it can never deliver aside, so that it would not hold back the others, no longer has to — answering it in `{ dead }` still saves its retries; a message it can deliver later is answered in `{ retry }`. A tenant resolver is no longer asked in an action of a per-tenant database's object, or in what the action calls: one that answered another tenant there (a tenant scope of its own around an action) is overruled by the object's tenant, and one that special-cased actions in the object (read its instance key when there was no request) can drop that — but not for the object's alarm, where the outbox sink runs and the resolver is still asked. A hand-built DoContext store without `tenantId` is read as its key only when no resolver is set. `createTestDatabase()` runs an action of a `global` database (`defineDatabase({ instance: 'global' })`, or its own `instance: 'global'` option) on the instance key `'global'`: the action's `ctx.instanceKey` is `'global'` and its envelopes' `tenantId` null, where 0.13.3 made both its `tenantId` option (`'test'` by default); `getTenantId()` in the action still answers that option. A hand-written `SqliteDurableObject` subclass used as a global database's object sets `databaseInstance = 'global'`: without it the object is per-tenant, and its envelopes say `tenantId: 'global'` for the key 'global', which 0.13.3 read as no tenant. Something that reads the outbox tables by hand finds `failed_at`, a negative `batch` (a suspect batch) and the `__outbox_sink` row. Sinks that return nothing keep working unchanged.
