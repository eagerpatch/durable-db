---
'durable-db': minor
---

The outbox says which database recorded a message, works out its tenant from what the build applied, and no longer lets one failing message hold back the rest.

- **The envelope names its database and its attempts.** `OutboxEnvelope` has `database` — the name the database is known by (the generated class's `databaseName`; a hand-written subclass without one, the name derived from its class name, else the class name) — and `attempts`, how many deliveries of it failed before this one. A global database's instance key `'global'` and a per-tenant database's tenant named `global` were the same string, and the envelope said nothing else: a sink could not tell them apart.
- **The tenant is worked out from what the build applied, not by cutting the key at its last `__dev_`.** The generated classes know their database's `instance` (`databaseInstance`) and the suffix the build gives their keys (`devEpochSuffix = applyDevEpoch('', name)`: `__dev_<epoch>` in dev, nothing in production). A global database's instance has no tenant whatever its key; a per-tenant one's tenant is its key without exactly that suffix. So `envelope.tenantId` and `getTenantId()` inside an action answer a tenant named `global` as that tenant, and keep a tenant id that contains `__dev_` whole — in production it was cut. The object hands its tenant to the action's DoContext store (`DoContext.tenantId`); a store built by hand without it is read as its key, `'global'` as no tenant.
- **Each message is retried on its own clock.** The outbox has a `next_attempt_at` column (an outbox an older version created gets it once, by `ALTER TABLE`); the alarm hands the sink only the messages that are due, oldest first, retries a failed one with its own backoff (5 s, doubling, at most 5 minutes) and is set to the earliest message due. A message the sink cannot take used to be retried with the 100 oldest forever, and nothing behind it was ever delivered. No order is kept across a failure: a message recorded later may be delivered before an earlier one waiting for its retry.
- **A sink may settle a delivery one envelope at a time**: `deliver()` may answer `{ retry: envelopes, error? }` — the envelope objects it was handed that it could not deliver; every other one counts as delivered. A throw still retries every envelope of the delivery. `queueOutboxSink()` answers the envelopes a failed `sendBatch` left unsent.
- **Not forever.** A message that failed `maxAttempts` deliveries — `durableDb({ outbox: { queue | module, maxAttempts } })`, default 100, about eight hours at the five-minute ceiling — is moved to the object's `__outbox_dead` table (message, instance key, `recorded_at`, attempts, last error, `dead_at`) and logged with `console.error`, naming how many and the table; it is never retried by itself and never dropped.
- `destroyDatabase()` no longer leaves the outbox unusable: the next message after it was refused with "no such table: __outbox".
- `createTestDatabase()`'s envelopes carry `database` and `attempts` too; its options `database` (default `'test'`) and `instance` (default: the action's own database's) name them.

**What a consumer changes.** `tenantOfInstanceKey(instanceKey)` is `tenantOfInstanceKey(instanceKey, { instance, devEpochSuffix? })`: a key alone cannot tell a global database's `'global'` from a tenant named so, and the one-argument call throws saying so. Code that builds `OutboxEnvelope`s (a sink's tests) adds `database` and `attempts`. A sink that worked around the tenant — reading `instanceKey` itself, or deciding `'global'` from whether the app has a global database — can use `envelope.tenantId` and `envelope.database` as they are. A sink that moved a message it can never deliver aside, so that it would not hold back the others, no longer has to — moving it aside at once still saves its retries; a message it can deliver later is answered in `{ retry }`. Sinks that return nothing keep working unchanged.
