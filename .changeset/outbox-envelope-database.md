---
'durable-db': minor
---

The outbox says which database recorded a message, works out its tenant from what the build applied, and no longer lets one failing message hold back the rest — or take the messages delivered with it down too; an outage of the sink costs a few deliveries a round of retries instead of one a message.

- **The envelope names its database and its attempts.** `OutboxEnvelope` has `database` — the name the database is known by (the generated class's `databaseName`; a hand-written subclass without one, the name derived from its class name, else the class name) — and `attempts`, how many deliveries of it failed before this one. A global database's instance key `'global'` and a per-tenant database's tenant named `global` were the same string, and the envelope said nothing else: a sink could not tell them apart.
- **The tenant is worked out from what the build applied, not by cutting the key at its last `__dev_`.** The generated classes know their database's `instance` (`databaseInstance`) and the suffix the build gives their keys (`devEpochSuffix = applyDevEpoch('', name)`: `__dev_<epoch>` in dev, nothing in production). A global database's instance has no tenant whatever its key; a per-tenant one's tenant is its key without exactly that suffix. So `envelope.tenantId` and `getTenantId()` inside an action answer a tenant named `global` as that tenant, and keep a tenant id that contains `__dev_` whole — in production it was cut. In dev every key carries an epoch, so a key that does not end with the current one is an earlier epoch's — an object `db reset` left behind, whose alarm still delivers what waits in its outbox — and its trailing `__dev_<epoch>` is cut: its tenant stays the tenant, not a made-up one with the old epoch in its name. The object hands its tenant to the action's DoContext store (`DoContext.tenantId`); a store built by hand without it is read as its key, `'global'` as no tenant.
- **Inside a per-tenant database's object, `getTenantId()` answers the object's own tenant first.** It asked an installed resolver first, and the resolver an app installs with `setTenantIdResolver()` at its worker module's top level is installed in every object's isolate too (in dev the worker and the objects share one): so the object's tenant was never read, and a resolver that reads a request threw inside an object — in an action, or in the stub of another database's action it calls. Now code running in a per-tenant object gets that object's tenant, which cannot be wrong there, before any resolver. A global database's object (no tenant of its own) and code outside any object ask the resolver as before. The one thing it changes: a resolver can no longer answer another tenant for code running inside a per-tenant object.
- **Each message is retried on its own clock.** The outbox has a `next_attempt_at` column (an outbox an older version created gets it, and `batch` below, once, by `ALTER TABLE`); the alarm hands the sink only the messages that are due, oldest first, retries a failed one with its own backoff (5 s, doubling, at most 5 minutes) and is set to the earliest message due. A message the sink cannot take used to be retried with the 100 oldest forever, and nothing behind it was ever delivered. No order is kept across a failure: a message recorded later may be delivered before an earlier one waiting for its retry.
- **One alarm, at most three deliveries.** The alarm reads the messages due (at most 100) and delivers them by the delivery they belong to, the oldest first. Once a delivery has delivered anything, the sink works, and everything else the alarm read goes in one more delivery. When the first delivers nothing, the second is tried; if that delivers anything, the first failure was its own and the rest goes in one; if it delivers nothing too — or the 100 read were one delivery that failed — the sink is down, and every message still due waits for the earliest retry the alarm set, its attempts not counted and nothing split. So an outage costs at most two failing deliveries a round of retries (one more for what is recorded in the meantime), however much is waiting, and when the sink is back the backlog goes 100 messages an alarm in at most three deliveries.
- **A message that fails every delivery holding it is cut off from the ones delivered with it.** A delivery that throws does not say which message failed it, so the messages it leaves are split in two for their retry (the outbox's new `batch` column), each half a delivery of its own, until the bad one is alone: of 100 messages pushed together, one of them bad, the other 99 are delivered within seven retries (about ten minutes) instead of failing with it until all 100 reach `maxAttempts`. A message recorded later never joins a retried batch (once a delivery of the alarm has gone through, it may go with the rest in the one after it).
- **`maxAttempts` counts a failure of the message's own.** A message that failed `maxAttempts` deliveries — `durableDb({ outbox: { queue | module, maxAttempts } })`, default 100, about eight hours at the five-minute ceiling — or that the sink answered in `{ dead }` is moved to the object's `__outbox_dead` table (message, instance key, `recorded_at`, attempts, last error, `dead_at`) and logged with `console.error`, naming how many and the table; it is never retried by itself and never dropped. Only a failure of its own buries it: a delivery of it alone, or one whose `{ retry }` named it. A delivery that threw with others in it counts the attempt and splits them, but buries none of them there — a message is buried once it has failed alone at or past the cap — so with `maxAttempts: 3` and one bad message among ten, the nine others are delivered, not buried beside it. An outbox 0.13 left is upgraded with its rows' `attempts` set to 0: 0.13 retried the 100 oldest together and counted each failure on every one of them, so its counts were its batch's — kept, the first failed delivery after the upgrade would have moved all of them to `__outbox_dead`.
- **A sink may settle a delivery one envelope at a time**: `deliver()` may answer `{ retry?, dead?, error? }` — of the envelope objects it was handed, those it could not deliver now (`retry`, retried together, not split: the sink said which) and those it never can (`dead`, moved to `__outbox_dead` at once, sparing them their retries); every other one counts as delivered. A throw still retries every envelope of the delivery.
- **The sink is handed a frozen list of its own.** `deliver(envelopes: readonly OutboxEnvelope[], …)` gets a frozen copy, and what it answers is matched by the envelope objects, never by their places in the list, so nothing a sink does to a list can make a message it never sent count as delivered. A sink that changes the list it is handed — chunking it with `splice()`, sorting it in place — fails loudly (a frozen array refuses it, and the delivery is retried whole); one that copies it first (`[...envelopes]`) chunks and sorts as it likes.
- **The Queue sink packs by bytes as well as by count.** `queueOutboxSink()` sent 100 messages to every `sendBatch`, so 100 messages of 3 KB (310 KB, over the 256 KB a `sendBatch` takes) were refused on every try, until all 100 reached `maxAttempts` and `__outbox_dead`; one message of 200 KB failed the 99 sent with it the same way. It now sends as few `sendBatch` calls as Cloudflare Queues takes — at most 100 messages and 256 KB each, a message's size its UTF-8 JSON plus the queue's 100 bytes — and sends each message with `contentType: 'json'`, so its size is its JSON's (a message is a JSON value already: its consumer gets the same body). A message over 128 KB, which no queue message holds, is not sent but answered in `{ dead }`, so it never fails the batch it would be in. A failed `sendBatch` still answers the envelopes it left unsent.
- **What it costs.** The outbox has no index — each would be a billed row written per message, and the table is near-empty but for an outage. An alarm reads it twice (the messages due, a scan that stops at the hundredth; then the earliest one waiting — after a full read the sink took, only whether one more is due), and when the sink is down the update that makes what is due wait scans it once more and writes each waiting message once, as a failed delivery of it would have. With about one alarm a round of retries, a long outage reads the table a few times a round, not twice for every batch waiting in it.
- `destroyDatabase()` no longer leaves the outbox unusable: the next message after it was refused with "no such table: __outbox". A delivery still in flight when it runs settles nothing on the storage that replaced the one it read (the object counts its storage generations), where it could have deleted, retried or buried a message recorded after the wipe that got the same id, or thrown "no such table".
- `createTestDatabase()`'s envelopes carry `database` and `attempts` too, and its `outbox` option is handed a frozen list of its own, as the sink is; its options `database` (default `'test'`) and `instance` (default: the action's own database's) name them.

**What a consumer changes.** `tenantOfInstanceKey(instanceKey)` is `tenantOfInstanceKey(instanceKey, { instance, devEpochSuffix? })`: a key alone cannot tell a global database's `'global'` from a tenant named so, and the one-argument call throws saying so. Code that builds `OutboxEnvelope`s (a sink's tests) adds `database` and `attempts`. A sink is typed `deliver(envelopes: readonly OutboxEnvelope[], …)` — one written against `OutboxEnvelope[]` still type-checks — and one that changes the list it is handed (`splice`, `sort`, `push`, …) copies it first, since the list is frozen. A sink that worked around the tenant — reading `instanceKey` itself, or deciding `'global'` from whether the app has a global database — can use `envelope.tenantId` and `envelope.database` as they are. A sink that moved a message it can never deliver aside, so that it would not hold back the others, no longer has to — answering it in `{ dead }` still saves its retries; a message it can deliver later is answered in `{ retry }`. A tenant resolver is no longer asked inside a per-tenant database's object: one that answered another tenant there (a tenant scope of its own around code running in the object) is overruled by the object's tenant, and one that only special-cased the object (read its instance key when there was no request) can drop that. Sinks that return nothing keep working unchanged.
