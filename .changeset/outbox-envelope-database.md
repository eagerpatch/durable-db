---
'durable-db': minor
---

The outbox says which database recorded a message, works out its tenant from what the build applied, and no longer lets one failing message hold back the rest — or take the messages delivered with it down too.

- **The envelope names its database and its attempts.** `OutboxEnvelope` has `database` — the name the database is known by (the generated class's `databaseName`; a hand-written subclass without one, the name derived from its class name, else the class name) — and `attempts`, how many deliveries of it failed before this one. A global database's instance key `'global'` and a per-tenant database's tenant named `global` were the same string, and the envelope said nothing else: a sink could not tell them apart.
- **The tenant is worked out from what the build applied, not by cutting the key at its last `__dev_`.** The generated classes know their database's `instance` (`databaseInstance`) and the suffix the build gives their keys (`devEpochSuffix = applyDevEpoch('', name)`: `__dev_<epoch>` in dev, nothing in production). A global database's instance has no tenant whatever its key; a per-tenant one's tenant is its key without exactly that suffix. So `envelope.tenantId` and `getTenantId()` inside an action answer a tenant named `global` as that tenant, and keep a tenant id that contains `__dev_` whole — in production it was cut. In dev every key carries an epoch, so a key that does not end with the current one is an earlier epoch's — an object `db reset` left behind, whose alarm still delivers what waits in its outbox — and its trailing `__dev_<epoch>` is cut: its tenant stays the tenant, not a made-up one with the old epoch in its name. The object hands its tenant to the action's DoContext store (`DoContext.tenantId`); a store built by hand without it is read as its key, `'global'` as no tenant.
- **Each message is retried on its own clock.** The outbox has a `next_attempt_at` column (an outbox an older version created gets it, and `batch` below, once, by `ALTER TABLE`); the alarm hands the sink only the messages that are due, oldest first, retries a failed one with its own backoff (5 s, doubling, at most 5 minutes) and is set to the earliest message due. A message the sink cannot take used to be retried with the 100 oldest forever, and nothing behind it was ever delivered. No order is kept across a failure: a message recorded later may be delivered before an earlier one waiting for its retry.
- **A message that fails every delivery holding it is cut off from the ones delivered with it.** A delivery that throws does not say which message failed it, so the messages a failed delivery leaves are split in two for their retry (the outbox's new `batch` column), each half a delivery of its own — the alarm makes one delivery at a time — until the bad one is alone: of 100 messages pushed together, one of them bad, the other 99 are delivered within seven retries (about ten minutes) instead of failing with it until all 100 reach `maxAttempts`. A message recorded later never joins a retried delivery. In a whole outage of the sink this costs no more deliveries than retrying each message alone.
- **A sink may settle a delivery one envelope at a time**: `deliver()` may answer `{ retry?, dead?, error? }` — of the envelope objects it was handed, those it could not deliver now (`retry`) and those it never can (`dead`, moved to `__outbox_dead` at once, sparing them their retries); every other one counts as delivered. A throw still retries every envelope of the delivery.
- **The Queue sink packs by bytes as well as by count.** `queueOutboxSink()` sent 100 messages to every `sendBatch`, so 100 messages of 3 KB (310 KB, over the 256 KB a `sendBatch` takes) were refused on every try, until all 100 reached `maxAttempts` and `__outbox_dead`; one message of 200 KB failed the 99 sent with it the same way. It now sends as few `sendBatch` calls as Cloudflare Queues takes — at most 100 messages and 256 KB each, a message's size its UTF-8 JSON plus the queue's 100 bytes — and sends each message with `contentType: 'json'`, so its size is its JSON's (a message is a JSON value already: its consumer gets the same body). A message over 128 KB, which no queue message holds, is not sent but answered in `{ dead }`, so it never fails the batch it would be in. A failed `sendBatch` still answers the envelopes it left unsent.
- **Not forever.** A message that failed `maxAttempts` deliveries — `durableDb({ outbox: { queue | module, maxAttempts } })`, default 100, about eight hours at the five-minute ceiling — or that the sink answered in `{ dead }` is moved to the object's `__outbox_dead` table (message, instance key, `recorded_at`, attempts, last error, `dead_at`) and logged with `console.error`, naming how many and the table; it is never retried by itself and never dropped.
- `destroyDatabase()` no longer leaves the outbox unusable: the next message after it was refused with "no such table: __outbox".
- `createTestDatabase()`'s envelopes carry `database` and `attempts` too; its options `database` (default `'test'`) and `instance` (default: the action's own database's) name them.

**What a consumer changes.** `tenantOfInstanceKey(instanceKey)` is `tenantOfInstanceKey(instanceKey, { instance, devEpochSuffix? })`: a key alone cannot tell a global database's `'global'` from a tenant named so, and the one-argument call throws saying so. Code that builds `OutboxEnvelope`s (a sink's tests) adds `database` and `attempts`. A sink that worked around the tenant — reading `instanceKey` itself, or deciding `'global'` from whether the app has a global database — can use `envelope.tenantId` and `envelope.database` as they are. A sink that moved a message it can never deliver aside, so that it would not hold back the others, no longer has to — answering it in `{ dead }` still saves its retries; a message it can deliver later is answered in `{ retry }`. Sinks that return nothing keep working unchanged.
