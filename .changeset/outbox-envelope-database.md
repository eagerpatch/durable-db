'durable-db': minor

The outbox says which database recorded a message, works out its tenant from what the build applied, and no longer lets a message the sink cannot take hold back the rest. In 0.13 such a message was retried with the 100 oldest forever, and nothing behind it was delivered.

- **The envelope names its database and its counted attempts.** `OutboxEnvelope` has `database` — the generated class's `databaseName`; for a hand-written subclass without one, the name derived from its class name, else the class name — and `attempts`, how many of its failures counted toward `maxAttempts` so far. A global database's key `'global'` and a per-tenant tenant named `global` were the same string before, and a sink could not tell them apart.
- **The tenant comes from what the build applied.** The generated classes know their database's `instance` (`databaseInstance`) and the suffix the build gives their keys (`devEpochSuffix = applyDevEpoch('', name)`: `__dev_<epoch>` in dev, nothing in production). A global database's instance has no tenant, whatever its key; a per-tenant one's tenant is its key without exactly that suffix. So `envelope.tenantId` and `getTenantId()` answer a tenant named `global` as that tenant, and keep a tenant id that contains `__dev_` whole. A dev key of an earlier epoch (an object `db reset` left behind) loses its trailing `__dev_<epoch>`. `tenantOfInstanceKey(key, { instance, devEpochSuffix? })` works it out the same way.
- **In an action of a per-tenant object, `getTenantId()` answers the object's own tenant first.** The resolver an app installs at its worker module's top level runs in every object's isolate too, and one that reads a request threw inside an action. The object hands its tenant to the action's DoContext store (`DoContext.tenantId`), which wins for the action and what it calls. A global database's object, code outside any object and an object's alarm (where the sink runs, reading `envelope.tenantId`) ask the resolver as before.
- **What a sink answers.** Nothing: every envelope was delivered. Or `{ retry?, dead?, error? }` of the envelope objects it was handed: those in `retry` were not delivered, those in `dead` never can be, and every other one counts as delivered. A throw is a `retry` of every envelope, and so is an answer that names an envelope it was not handed, or one in both lists. The sink is handed a frozen copy of its list, typed `readonly OutboxEnvelope[]`, and envelopes are paired with their rows before the call: nothing a sink does to its list makes an unsent message count as delivered.
- **A failure alone counts; a group's never does.** The alarm hands the sink the oldest messages due, those that never failed alone first, at most 100 in a call. What a call did not deliver is halved, and both halves are tried next in the same alarm, so a bad message ends up alone while the rest are delivered: of 100 messages with one bad, the other 99 go in that alarm. A group that fails moves no clock and counts nothing. A message that fails alone is retried on its own backoff (5 s, doubling, at most 5 minutes; the new `tries`, `next_attempt_at`), and the failure counts toward `maxAttempts` only when the sink settled some other message since the message was recorded or last failed (`failed_after` against the new `__outbox_sink.settled`).
- **When the sink is down.** A failure alone in an alarm that settled nothing cannot be told from an outage, so the sink is taken for down (`__outbox_sink.down_until`). Until its next try nothing is tried, and a message recorded meanwhile sets no alarm of its own. The next try hands the sink one message of those that failed alone least often — the newest of them at one try, the oldest at the next — and backs off like a message does. When it settles, the outage is over and the alarm goes on. When the message that took the sink for down, or the one the last try handed it, had failed alone before (`down_tried`), its failure may be its own: the next message recorded brings the try forward, and that try hands the sink a message that never failed alone.
- **The cap and `__outbox_dead`.** A message the sink answers in `{ dead }`, or that reaches `maxAttempts` counted failures — `durableDb({ outbox: { queue | module, maxAttempts } })`, default 100, at least 2 — is moved to the object's `__outbox_dead` table and logged. It is never retried by itself and never dropped. An outage counts at most one failure a message, so it buries only a message that already had `maxAttempts` − 1 counted failures. A sink's error is kept as text even when `String()` cannot convert it.
- **What it costs.** An alarm makes at most 16 sink calls. An outage costs at most 8 in the alarm that notices it, then one call and two rows written a round, whatever waits. A message recorded meanwhile adds nothing, unless the last try handed the sink a message that had failed alone before: then it brings the next try forward, at most one more call a round. Measured with a sink that always throws, over an hour: with 2 000 waiting, 17 alarms, 24 calls and 34 rows written (0.13.3: 17, 17 and 1 700); with a message recorded every 10 s, 17 alarms, 17 calls and 34 rows written besides the messages (0.13.3: 361, 361 and 31 051). The outbox has no index: each would be a billed row written per message.
- **The Queue sink packs by bytes.** `queueOutboxSink()` stays within 100 messages and 256 KB a `sendBatch`, a message's size its UTF-8 JSON plus the queue's 100 bytes, and sends each with `contentType: 'json'`. A message over 128 KB is answered in `{ dead }`. A failed `sendBatch` answers the envelopes it left unsent in `{ retry }`; the batches before it were delivered.
- **The upgrade.** An outbox 0.13 left gets the new columns once, by `ALTER TABLE`, and its rows' `attempts` set to 0: 0.13 counted each failure on every one of the 100 oldest.
- **`destroyDatabase()`.** The outbox is created again after it; the next message was refused with "no such table: __outbox". A call still in flight when it runs settles nothing on the storage that replaced the one it read.
- `createTestDatabase()`'s envelopes carry `database` and `attempts` too (options `database`, default `'test'`, and `instance`, default the action's own database's), and its `outbox` option is handed a frozen list, as the sink is.

**What a consumer changes.** `tenantOfInstanceKey(key)` is `tenantOfInstanceKey(key, { instance, devEpochSuffix? })`; the one-argument call throws. Code that builds `OutboxEnvelope`s adds `database` and `attempts`. A sink that changes its list (`splice`, `sort`, `push`) copies it first. A sink that worked around the tenant or the database can read `envelope.tenantId` and `envelope.database`. A tenant resolver is no longer asked in an action of a per-tenant object, or in what the action calls. `createTestDatabase()` runs an action of a `global` database on the key `'global'`, its envelopes' `tenantId` null. A hand-written `SqliteDurableObject` subclass used as a global database's object sets `databaseInstance = 'global'`. Sinks that return nothing keep working unchanged.
